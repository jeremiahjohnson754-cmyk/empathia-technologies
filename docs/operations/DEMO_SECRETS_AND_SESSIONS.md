# Secrets, sessions and expiry on the hosted demonstration

Founder, 17 Nov 2026: "Establish backup, restore, secret-management, and demo-session expiration procedures."
Backup and restore are in `DEMO_BACKUP_AND_RECOVERY.md`. This file is the other two.

Two statements first, so that nothing below is read as more than it is (founder, the same day: "don't confuse successful API
security tests with a complete independent security audit, or a working backend with the entire demo website being connected"):

- The tests named here are this project's own. **No independent security audit has been made** of the API, the deployment or the site.
- The hosted API serves one page of the demo, `#/connected`. **Every other page of the demo still keeps its records in the browser.**

## Secrets

| Secret | What it does | Where it lives | Who can read it |
|---|---|---|---|
| `DEMO_SESSION_SECRET` | signs demonstration sessions; nothing else is signed or accepted in this mode | generated by the platform when the Blueprint is first synced (`generateValue`) | whoever can open the service's environment on the platform |
| `EMPATHIA_APP_PASSWORD`, `EMPATHIA_WORKER_PASSWORD` | the two runtime roles' database passwords; the start command sets them on the roles at every start | generated by the platform | the same |
| `DATABASE_URL` | the schema owner's connection, used by the three preparation steps only; the API itself connects as the runtime role | supplied by the platform from the database it created | the same |
| a sandbox's key | opens one sandbox as any of its sixteen synthetic people (one for each of the fifteen roles, and a second service technician) | shown once to the visitor who opened it; the database keeps only its SHA-256 | the visitor, and anyone they give the resume code to |

Rules that hold, each with its check:

- **No secret is in the repository.** The Blueprint declares the three as generated and the URL as coming from the database:
  `validate-blueprints.py` P3-7 and P3-8.
- **No secret is in a chat, a log line or a test's evidence.** The start command prints roles and actions, never a value. Evidence files
  are searched for key-shaped strings before they are committed.
- **The runtime role is not the owner and can do nothing but sign in**: rehearsal R-05.
- **A value typed where it should not have been is treated as exposed** and rotated; it is never reused.

### Rotating

Rotation is a restart with new values. Rehearsed every test run (R-11):

| Rotate | How | What it does to people using the demo |
|---|---|---|
| the session secret | set a new `DEMO_SESSION_SECRET` on the service (the platform can generate one) and let it redeploy | **every session stops at once.** No sandbox is lost: the page asks for a new session with the sandbox's key and carries on, and a visitor in another browser resumes with the code as before. The per-address hourly opening count starts again, because it is salted from this secret |
| a runtime-role password | set a new value; on the next start the role step sets it on the role | none. The old password no longer connects (R-11) |
| the owner's password | on the platform (the database's credentials); the service's `DATABASE_URL` follows from the Blueprint | a restart |
| a sandbox's key | it cannot be changed. **Reset** closes the sandbox and opens a new one with a new key; the old key and its sessions stop at once | that visitor starts with an empty sandbox |

When exposure is suspected: rotate the session secret first (it ends every session in one step), then the role passwords, then look
at the audit history of the affected sandboxes. The records are synthetic; the procedure is the one real records would need.

Not done: a rotation on the hosted service. It has been rehearsed locally only.

## Sessions and sandboxes: how long each lasts, and what ending looks like

| | Lasts | When it ends |
|---|---|---|
| A session (one person of one sandbox) | 30 minutes (`DEMO_SESSION_TTL_SECONDS`, between 1 minute and 1 day) | the page asks for a new one with the key, once, and repeats what it was doing. The visitor sees nothing. Sessions are held in memory only: closing the tab ends them |
| A sandbox | 72 hours from opening (`demo.js enable --ttl-hours`) | its key opens nothing and every session of it stops: "the sandbox is unknown, closed or expired, or the key is not right". The page says the sandbox is no longer there and offers a new one. Rehearsed: R-12; tested: `demo-sandbox.test.mjs` |
| A sandbox that is reset | until the reset | the same, at once; the new one has nothing recorded |
| What the browser keeps | the sandbox's id, key, tenant name, room code and expiry time, in local storage | "Forget it in this browser" removes it. The sandbox stays on the server until it expires |

Limits that bound a sandbox while it lives: 200 open at once, 12 opened per address per hour, 5,000 in all per database, 4,000
recorded actions and 60 evidence notes each (`demo.js enable`). At a ceiling the visitor is told the demonstration is full or that
the sandbox has reached its limit.

### What is kept after a sandbox ends

**Everything.** The API never deletes a sandbox: an expired, closed or reset sandbox's records stay in the database, unreachable by
any key (R-12 counts them). That is deliberate for an audit history, and it means retention is decided by how long the database lives:

- on the free plan the database expires 30 days after it was created, and every sandbox with it;
- on a paid plan nothing expires, so the database has to be recreated on a schedule, or ended sandboxes removed by a job that does
  not exist yet. Until one or the other is in place the honest retention statement is **"kept until the database is recreated"**.

The demo page tells a visitor that the sandbox is synthetic, theirs alone until it expires or is reset, and that nothing personal or
confidential should be typed into it. It does not yet state how long ended sandboxes are kept. That sentence should be added with the
schedule, when the schedule is decided.
