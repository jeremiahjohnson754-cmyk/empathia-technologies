# Render deployment from GitHub — repository, settings, order (2026-10-31)

Supersedes the deployment *method* in [RENDER_STAGING.md](RENDER_STAGING.md) (prebuilt image from a registry, written when no Git provider
was connected). That document's account audit, Hobby/Pro analysis, privacy model (§3) and risks (§8) still apply. **Nothing has been
created, deployed or provisioned.** Every step below that touches GitHub or Render is an owner action.

Two deployments, kept separate on purpose:

| | Phase 1 — public, synthetic | Phase 2 — authenticated enterprise application |
|---|---|---|
| What | `empathia-website` (marketing site) and `empathia-demo` (investor demonstration, synthetic data, runs in the browser) | `empathia-api` (API + outbox worker), `empathia-app` (enterprise web app), `empathia-db` (PostgreSQL 16) |
| Blueprint | `render.yaml` (repository root) | `deploy/render/enterprise.render.yaml` (custom Blueprint Path) |
| Data, secrets | none; no API calls; lead forms say "not configured" and cannot submit | tenant data under forced row-level security; secrets generated by Render or entered in the dashboard |
| Cost | $0 (static sites) | paid (§6) |
| Gate | A0 (owner: external distribution of the demo), A2-public | A1, A2, A3, A5, then gates V-1 and V-2 on Render |

**Do not connect or deploy the old `empathiaOS` repository.** Both Blueprints name repository-relative paths that exist only in this one.

## 1. The repository

**Direct push from this session: not possible.** The session's GitHub CLI has no valid token ("No linked GitHub account") and the
repository listing tool reports no linked account. Hence a verified Git bundle, restored and pushed from your computer.

What the bundle preserves (checked with `git fsck --full --strict`, `git bundle verify`, and a test clone compared ref by ref): branch
`main` with its full history, every tag, every tracked file (migrations `database/migrations/0001…0025`, all packages and apps,
configuration templates, `tests/evidence/`). Not in Git, by design: `.local/` (local database and its credentials), `node_modules/`,
`dist/`, generated datasets, video files. The tracked files are secret-scanned before packaging (`SECRET_SCAN.json`).

On your computer (Git 2.30+; the GitHub CLI `gh` is optional):

```bash
# 0. check what you downloaded
sha256sum -c empathia-technologies.bundle.sha256          # macOS: shasum -a 256 -c empathia-technologies.bundle.sha256
git bundle verify empathia-technologies.bundle            # "… is okay"

# 1. restore with full history
git clone --branch main empathia-technologies.bundle empathia-technologies
cd empathia-technologies
git log -1 --format='%H %s'                               # must print the commit stated with the bundle
git tag | wc -l                                           # the tag count stated with the bundle

# 2. create the EMPTY private repository (no README, .gitignore or licence — they would create a conflicting first commit)
gh repo create empathia-technologies --private --description "Empathia Technologies platform"
#    or in the browser: https://github.com/new → name empathia-technologies → Private → leave every "initialize" box unticked

# 3. push
git remote rename origin bundle                           # the clone's "origin" is the bundle file
git remote add origin https://github.com/<your-github-user>/empathia-technologies.git
git push -u origin main
git push origin --tags

# 4. confirm GitHub has exactly what the bundle had
git ls-remote origin | sort -k2 > /tmp/remote.txt; git show-ref | sort -k2 > /tmp/local.txt; diff /tmp/local.txt /tmp/remote.txt && echo IDENTICAL
```

Then in GitHub: Settings → General confirms **Private**. On push, `.github/workflows/ci.yml` runs the build and the test matrix on GitHub
Actions (private-repository minutes on your plan). Its first run is the first independent build of this code outside this workspace —
look at it before Render builds anything.

Render: Dashboard → Account/Workspace Settings → Git → GitHub → configure the Render app's repository access → **Only select
repositories → `empathia-technologies`** (remove `empathiaOS` from the selection, or leave it unused).

Alternative: link GitHub to this session (claude.ai → Settings → Connectors → GitHub) and a later session can push directly. Not needed.

## 2. Phase 1 — website and investor demo (free static sites)

Render: **New → Blueprint** → repository `empathia-technologies` → branch `main` → Blueprint Path `render.yaml` → review → Apply. Render
shows the two static sites it will create; nothing paid is in this file. Equivalent manual settings (New → Static Site), per site:

| Setting | empathia-website | empathia-demo |
|---|---|---|
| Repository / branch | `empathia-technologies` / `main` | same |
| Root Directory | (blank — the repository root; the build needs the workspace) | same |
| Build Command | `npx --yes pnpm@10.18.3 install --no-frozen-lockfile && node scripts/build.mjs --public` | same |
| Publish Directory | `apps/website/dist` | `apps/demo/dist` |
| Environment | `SKIP_INSTALL_DEPS=true`, `NODE_VERSION=22.22.0` | same |
| Headers (path `/*`) | Content-Security-Policy (exact value in `render.yaml`), X-Content-Type-Options `nosniff`, X-Frame-Options `DENY`, Referrer-Policy `no-referrer`, Strict-Transport-Security `max-age=31536000` | the same plus X-Robots-Tag `noindex, nofollow` |
| Auto-deploy | on commit | on commit |

The build (`build.mjs --public`) type-checks and builds only the shared UI, the website and the demo, then runs the distribution
hygiene check; it never builds the API, the Founder Studio or anything confidential. The sitemap and robots.txt take their base URL
from `RENDER_EXTERNAL_URL` (set `WEBSITE_BASE_URL` when a custom domain is added). The URLs will be
`https://empathia-website.onrender.com` and `https://empathia-demo.onrender.com`, or with a suffix Render adds if a name is taken.

The **investor demo** is a separate site so that sharing its URL never shares the enterprise application, and vice versa. Its status in
`docs/demonstrator/` is *INVESTOR_DISCLOSABLE after security and owner approval*; deploying it creates a URL anyone can open, so
whether and with whom it is shared is decision **A0** (yours). `noindex` keeps it out of search results; it is not access control.

After the first deploy, from any computer:

```bash
for u in https://empathia-website.onrender.com/ https://empathia-demo.onrender.com/; do
  curl -sSI "$u" | grep -iE '^(HTTP|content-security-policy|strict-transport|x-frame|x-robots)'; done
```
Then open both in a browser: the website's pages, `/contact/` (form disabled, "not configured"), the demo's `#/investor` (labelled
synthetic). These are the same checks `scripts/staging/verify-static.mjs` ran locally (§7).

## 3. Phase 2 — the enterprise application (paid; after approvals)

Prerequisites: A1 (spend), A2 (two public `*.onrender.com` URLs protected by authentication, not by network), **A3 (an OIDC identity
provider: issuer, API audience, JWKS URL, a test user)**, and **A5 (UI sign-in, §5 B-2)**. Without A3 the API refuses to start in
production mode (by design), so the deploy fails at its health check.

Render: **New → Blueprint** → `empathia-technologies` / `main` → Blueprint Path **`deploy/render/enterprise.render.yaml`**.

### Services and database

| | empathia-db | empathia-api | empathia-app |
|---|---|---|---|
| Type | PostgreSQL **16**, plan `0.1c-256mb`, 1 GB, region oregon | Web service, runtime **Docker**, plan `0.5c-512mb`, oregon | Web service, runtime **Docker**, plan `0.5c-512mb`, oregon |
| Dockerfile / context | — | `./deploy/render/Dockerfile` / `.` | the same image |
| Start (Docker command) | — | `node services/enterprise-api/dist/src/main.js` | `node apps/enterprise-web/server/serve.mjs` |
| Pre-deploy | — | `bootstrap.js --roles && migrate.js && bootstrap.js --policy` (full paths in the Blueprint) | — |
| Health check | — | `/health` | `/healthz` |
| Storage | 1 GB | persistent disk `evidence` at `/data/objects`, 1 GB | none |
| Network | `ipAllowList: []` — private network only | public URL | public URL |
| Auto-deploy | — | off (Manual Deploy) | off |

The region must be the same for all three; change it in all three places before applying if Oregon is not wanted (it cannot be changed
after creation, nor can the Postgres version, database name or user).

The image: a build stage installs the pinned dependencies and runs the full `node scripts/build.mjs` (type checks, API contract check,
hygiene); the runtime stage holds only the assembled runtime tree (compiled JavaScript, migrations, the web app's static build — no
TypeScript, tests, docs, Founder Studio or secrets), runs as uid 10001. Both web services build it; Render builds once per service.

### Environment variables

| Service | Name | Source | Purpose |
|---|---|---|---|
| api | `DATABASE_URL` | from `empathia-db` connectionString | schema owner: pre-deploy and operator bootstrap only |
| api | `EMPATHIA_APP_PASSWORD`, `EMPATHIA_WORKER_PASSWORD` | generated by Render | passwords of the runtime roles; the API derives `empathia_app` / `empathia_worker` URLs from `DATABASE_URL` |
| api | `JWT_SECRET` | generated by Render | signs short-lived internal tokens (≥ 32 bytes) |
| api | `PGSSLMODE=require` | value | TLS to the database |

| api | `OIDC_ISSUER`, `OIDC_AUDIENCE`, `OIDC_JWKS_URL` | **you enter** (A3) | identity provider; JWKS must be https |
| api | `OIDC_LINK_BY_EMAIL=on` | value | the bootstrapped administrator's verified email binds on first sign-in |
| api | `CORS_ORIGINS` | **you enter**: `https://empathia-app.onrender.com` | only the web app may call the API from a browser |

| image | `HOST=0.0.0.0`, `OBJECT_STORE_DIR=/data/objects` | Dockerfile | |

If Render assigns a URL with a suffix (name taken), correct `CORS_ORIGINS` and `API_URL` after creation and redeploy both.

### Deployment order

| # | Step | Expected | If not |
|---|---|---|---|
| E1 | Apply the Blueprint; enter the five `sync: false` values | Render creates `empathia-db` first, then both services | — |
| E2 | `empathia-api` first deploy: build → **pre-deploy** | log shows `{"defaultUser":"empathia_owner","v1":"PASS",…}`, then 25 migrations applied, then `{"policy":"loaded",…}` | `roles refused: V-1 failed` → **stop** (§4 V-1); the deploy fails and nothing runs as the owner |
| E3 | API health | `https://empathia-api.onrender.com/health`: `status` ok, `migrationsApplied` 25, `release.sha` = the commit, `evidenceStoreWritable: true` | `evidenceStoreWritable: false` → §4 V-2 |
| E4 | Operator bootstrap, once — Render Dashboard → `empathia-api` → Shell: `node services/enterprise-api/dist/src/db/bootstrap.js --tenant=<slug> --tenant-name="<name>" --site=SITE-HQ:"Headquarters" --building=HQ1:"Main building":6:SITE-HQ --admin-email=<your IdP email> --admin-name="<name>"` | JSON with the tenant id; every step in the tenant's audit trail (`platform.bootstrap.*`) | refuses a synthetic slug or a malformed email |
| E5 | `empathia-app` deploy | `/healthz` 200; the page loads with a CSP naming the API origin | 421 = host not allowed (check `WEB_ALLOWED_HOSTS`) |
| E6 | Deployment tests from your computer: `node scripts/staging/smoke.mjs --api=https://empathia-api.onrender.com --web=https://empathia-app.onrender.com --expect-sha=<commit> --expect-auth=oidc --out=tests/evidence/STAGING_SMOKE.json`, then again with `--token=<IdP access token> --tenant=<slug> --role=secadmin` | D1–D9 PASS, then D10 PASS | each failure names its check |
| E7 | Invite testers (`POST /v1/admin/invitations`); optionally a second tenant (`--tenant=isolation-probe`) so a tester can verify tenant isolation | | |

Migrations are forward-only and additive, applied in file order, each in its own transaction and recorded with its SHA-256; a changed
applied file is refused. The pre-deploy step runs on every deploy and is idempotent (roles re-passworded to the same values, applied
migrations skipped, policy reloaded).

## 4. Gates that can only be checked on Render

| ID | Question | How it is checked | If it fails |
|---|---|---|---|
| V-1 | Can Render's database user create roles? The tenant boundary needs runtime roles that are not the owner and have `NOBYPASSRLS` | `bootstrap.js --roles` in pre-deploy (E2); refuses rather than continuing | Do not run the API as the owner. Ask Render support, or use another managed Postgres; the Blueprint is then edited, not weakened |
| V-2 | Is the persistent disk writable by the image's non-root user (uid 10001)? | `evidenceStoreWritable` in `/health` (E3); smoke D1 fails on `false` | Evidence uploads would fail. Do not switch the image to root without a review; report the mount owner/permissions first |
| V-3 | Does Render's Docker build succeed (dependency install without a lockfile, the full build)? | The first deploy's build log; GitHub Actions CI runs the same build first | Read the log; commit a `pnpm-lock.yaml` (`pnpm install --lockfile-only`) for a frozen, reproducible install |
