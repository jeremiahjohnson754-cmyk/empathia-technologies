# Private assets and the full regression

Founder, 17 Nov 2026: "Founder Studio keeps failing in the isolated regression worktree because its private assets aren't there…
The proper solution is a reproducible private-asset provisioning process that keeps credentials and licensed content protected while
allowing the entire test suite to run consistently in a clean environment. Otherwise, the team could end up saying 'everything
passed except the thing we always exclude.'" And: "Remove that recurring regression exception permanently."

## What was wrong

Every regression since 12 Nov reported 105 of 106 browser suites passing in the clean worktree, with `founder-studio` rerun by hand in
the one checkout that still held a studio built on 12 Nov. The cause was never the code: the studio embeds the Founder Edition page
and plays the founder's films, both of which are private and are not in the repository. A clean checkout had neither, and nothing
put them there. The only copy of the Founder Edition page on this workstation was inside that one old build directory, which any
rebuild would have erased.

## What is private, and what is not

| | Where it lives | In the repository |
|---|---|---|
| The Founder Edition page (one HTML file, 7 MB) | the private store | its name, size and SHA-256 only |
| The founder's films (five on this workstation, 516 MB) | the private store | their names, sizes and SHA-256 only (the curated list already named them) |
| The studio's data (`apps/founder-studio/src/generated/`) | generated by the studio's own build from the checkout's records | ignored: it is a build product, regenerated for each commit, not a private input |
| The built studio (`apps/founder-studio/dist/`) | built in the checkout; the page is copied into it and the films are linked into it | ignored |

No credential is involved anywhere in this: provisioning reads local files and downloads nothing.

## The pieces

- **The store**: a directory outside the repository, `EMPATHIA_PRIVATE_STORE` (default `~/.empathia-private`), subdirectory
  `founder-studio`, readable by its owner only (directories 700, files 600).
- **The manifest**: `apps/founder-studio/PRIVATE_ASSETS.json`, committed. One entry per private file: path within the store, bytes,
  SHA-256, and what it is for. It lets any copy of the store be checked and holds none of the content.
- **The command**: `scripts/private/founder-studio-assets.mjs`.

| | |
|---|---|
| `status` | what the manifest asks for, and whether the store holds it |
| `verify` | every file present with the size and hash the manifest names; exit 1 otherwise, each difference named |
| `provision [--checkout=<dir>]` | verify, then build that checkout's studio: its data from that checkout's records, the page from the store, the films linked from the store. Refuses a store that does not match the manifest |
| `snapshot [--from=<checkout>]` | fill the store from a checkout whose built studio has the assets, and rewrite the manifest. Used once, on 17 Nov, to rescue the files from the old build directory; used again only when the founder supplies a new page or film |

`node scripts/build.mjs --studio` now provisions from the store too (an explicit `--founder-edition=<path>` still works).

## What happens without the assets

- `provision` fails, saying `NOT PROVISIONED` and why (no store; a file missing; a file with different content).
- The studio's browser suite does not start. It prints `NOT RUN founder-studio — <why>. Provision this checkout first: …` and exits
  **3**. It used to fail at its first product page with an error that named no cause.
- `scripts/test.mjs` records a suite that exits 3 with a `NOT RUN` line as `NOT_RUN` with that reason; `no-unexpected-skips.mjs`
  already refuses a release with a NOT_RUN that is not on its short list, and the studio is not on it.
- The regression report (below) counts it as not passed and reports the commit `NOT COMPLETE`.

A NOT RUN is never a pass. None of the suite's nineteen checks was changed.

## The regression procedure, now in the repository

`scripts/release/regression.mjs`, run from a clean worktree of the commit to be staged. Until today the runner was a pair of shell
scripts outside the repository.

    node scripts/release/regression.mjs prepare
    node scripts/release/regression.mjs base
    node scripts/release/regression.mjs browser --scheme=light --part=1/4 --restore-evidence     (… 2/4, 3/4, 4/4; then dark)
    node scripts/release/regression.mjs report

- `prepare` builds everything, then provisions the studio from the store and builds it.
- `report` takes the list of browser suites from `tests/browser/` itself, in both colour schemes. There is no list of suites that may
  be missing: a suite never run, or NOT RUN, or run with uncommitted changes in the checkout, makes the commit `NOT COMPLETE` and the
  command exit 1. `COMPLETE` is printed only when the build, the provisioning, the base suites and every browser suite in both
  schemes passed.

## Verified on 17 Nov 2026

- The store was filled from the old build and verified against the manifest: 6 files, 522.9 MB.
- The clean regression worktree (the commit `e3c8e9f`, no private file in it) was provisioned from the store, and `founder-studio`
  then passed **there**: 19 passed, 0 failed in light, and 19 passed, 0 failed in dark. Before provisioning, the same suite in the
  same worktree failed.
- Then the committed procedure, on the commit that introduced it (`1cba676`), in the same worktree with its studio build and
  generated data removed first: the suite alone said `NOT RUN founder-studio — the studio is not built` and exited 3;
  `regression.mjs prepare` built everything (51 s) and provisioned the studio (3 s, 6 private files verified);
  `regression.mjs browser` passed `founder-studio` in light and in dark; `regression.mjs report` said `NOT COMPLETE`, correctly,
  because the other 105 suites and the base suites had not been run for that commit.
- `tests/unit/private-assets.test.mjs` PA-01…06, part of `node scripts/test.mjs`: the manifest holds names, sizes and hashes only;
  none of the private files is tracked; the default store is outside the repository; no store, a missing file and an altered file
  are each refused and named; the studio suite on a studio without its files exits 3 with `NOT RUN` and reports no pass.

## Not solved here, and whose decision it is

- **Durability.** The store is on this workstation, which is an ephemeral machine. If it is reclaimed, the page and the films exist
  only wherever the founder keeps the originals. The process is then: put the files in a store directory on the new machine and run
  `verify`; the manifest says exactly which files, and proves they are the same ones. **Where a durable private copy is kept (an
  encrypted archive in the founder's own storage, a private bucket, or nowhere but the founder's computer) is the founder's decision.**
  A private bucket would mean an account, a small charge and a credential held as a secret; none of that has been set up.
- **A hosted CI runner** would need the same store mounted from a secret location. There is no hosted CI for this suite today; it
  runs on this workstation.
- The other 31 curated films are not on this workstation at all. The studio lists them and says which are present; the suite needs
  only the ones that are.
