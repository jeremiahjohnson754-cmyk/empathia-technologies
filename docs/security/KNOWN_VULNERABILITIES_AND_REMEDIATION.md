# Known vulnerabilities and remediation status

Honest list of weaknesses known in the production starter on 2026-10-26. Status values: **OPEN** (must be fixed before production),
**ACCEPTED_FOR_STARTER** (acceptable only for local development on synthetic data), **N/A** (explained). "Owner" is a suggested
role in the future team (`docs/engineering-handoff/`), not an assignment.

| ID | Weakness | Where | Impact | Status | Remediation | Suggested owner |
|---|---|---|---|---|---|---|
| KV-01 | Development identity provider signs tokens with a symmetric HS256 secret held by the API | `services/enterprise-api/src/auth/jwt.ts`, `config.ts` | Whoever obtains the secret can mint tokens for any person and role | ACCEPTED_FOR_STARTER (refused in production, `config.ts:35`) | OIDC with RS256/JWKS verification behind the existing `TokenVerifier` interface; the API holds no signing key | Backend/security lead |
| KV-02 | No OIDC and no MFA | — | Identity assurance depends on a shared development password | OPEN | Customer IdP via OIDC; MFA enforced at the IdP | Security lead |
| KV-03 | Access token stored in `sessionStorage` in the web app | `apps/enterprise-web/src/api.ts:13,21` | An XSS bug would expose the token (mitigated by React escaping and a strict CSP) | ACCEPTED_FOR_STARTER | Backend-for-frontend with HttpOnly, Secure, SameSite=Strict session cookie; then add CSRF tokens | Frontend lead |
| KV-04 | Rate limit is an in-memory token bucket per process | `services/enterprise-api/src/http/server.ts:20,59` | Limits reset on restart and do not add up across instances | ACCEPTED_FOR_STARTER | Edge/WAF rate limiting plus a shared limiter | Platform engineer |
| KV-05 | No TLS between API and PostgreSQL locally | `scripts/db.mjs:54` (127.0.0.1 only) | Traffic readable on a shared host | ACCEPTED_FOR_STARTER | `sslmode=verify-full` with the managed database's CA (client supports TLS, `db/pg.ts`) | Platform engineer |
| KV-06 | Evidence stored only in `LocalObjectStore`; S3 adapter is CONTRACT_ONLY | `services/enterprise-api/src/storage/objectStore.ts:36-44` | No versioning, object lock or off-site copy; disk loss loses evidence | OPEN | Implement `S3ObjectStore` with versioning + object lock; see `docs/architecture/STORAGE.md` | Backend lead |
| KV-07 | No malware scanning of evidence uploads | `domain/commissioning.ts:27-35` (type allow-list and name sanitizing only) | A malicious file can be stored and downloaded by another user | OPEN | Scan on upload (quarantine bucket → scan → release); keep `Content-Disposition: attachment` | Security lead |
| KV-08 | Worker cross-tenant policies keyed on a settable session variable (`app.worker = on`) | was `database/migrations/0004_platform.sql:43-44,73,97` | Code running as the runtime role could have read other tenants' outbox/notification/read-model rows (required a separate flaw) | **FIXED** — migration `0008_worker_role.sql`: policies admit only the role `empathia_worker`, which has column-limited grants; the API's outbox worker connects with `WORKER_DATABASE_URL`; regression test in `tests/security/authz.test.mjs` | Backend lead |
