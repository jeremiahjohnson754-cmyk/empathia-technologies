# How to add a domain

Two kinds of "domain" come up: (A) a new **commissioning domain or discipline pack** (new tests that apply to some rooms), and
(B) a new **product domain** (a new kind of record and workflow, e.g. Intake requests). Paths are relative to the repository root.

## Where the rule data lives today — read this first
The commissioning rule data (`packages/domain-data/data/*.json`: test library `V25_TESTS.json`, pack tests `V25_CX_CATALOGUE.json`,
packs `V25_CX_PACKS.json`, rule pack `V25_DESIGN_rulePack.json`, domain → persona `V25_DOMAIN_PERSONA.json`, verifier personas,
templates, categories, archetypes, personas, events) is **extracted unchanged from the 2.5.4 demonstrator build** by
`scripts/extract/extract-domain-data.mjs`, with hashes in `packages/domain-data/data/PROVENANCE.json`. The TypeScript engine must
reproduce the demonstrator on **92 golden cases** (`packages/domain-data/golden/room-engine-golden.json`, generated by
`scripts/extract/extract-golden.mjs`; `packages/commissioning-engine/test/parity.test.ts` says: *never edit the golden file to make a
test pass; regenerate it only from a new demonstrator build*).

So adding rules has two possible routes, and **the founder and CTO must choose one** (technical debt item TD-11):

* **Route 1 — demonstrator stays the source of truth.** Change the demonstrator source (in a new branch, never a frozen release),
  rebuild it, re-run both extractors, review the data diff, and keep the parity suite green. Slow, but one rule set.
* **Route 2 — the monorepo becomes the source of truth (recommended for a commercial product).** Freeze the demonstrator parity file as
  "2.5.4 parity", edit `packages/domain-data/data/*.json` directly from then on, and add a second, hand-reviewed golden file for new
  behaviour (e.g. `packages/domain-data/golden/starter-golden.json`) with its own test. Record the switch in `PROVENANCE.json`.

## A. Adding a commissioning domain or discipline pack (Route 2 shown)

1. **Specify** each test with the domain engineer: id, label, domain, phase (1–5), tier, verifier, method, accepted evidence kinds
   (`accepts`, e.g. `FIELD_OBSERVED`, `INSTRUMENT_MEASURED`, `ENGINEER_APPROVED`), whether it is instrument-measured, whether it can be
   not-applicable or waived, its dependencies (`deps`), and **when it applies** (`applies`: device families, room tiers, archetypes or
   project types). See an existing entry, e.g. `audio_noise_floor` in `V25_CX_CATALOGUE.json`.
2. **Data**: add the pack to `V25_CX_PACKS.json` and its tests to `V25_CX_CATALOGUE.json` (or base tests to `V25_TESTS.json` and the
   rule pack in `V25_DESIGN_rulePack.json`). Map the domain to its responsible persona in `V25_DOMAIN_PERSONA.json` and, if a new
   specialist verifies it, to `V25_VERIFIER_PERSONAS.json`. Use **existing** persona authorities (e.g. `test.verify.audio`); a new
   specialist role is a product decision reviewed by security.
3. **Engine**: usually no code change — `packages/commissioning-engine/src/applicability.ts` (`requiredTests`, `packApplies`,
   `computeApplicability`) reads the tables. If the applicability condition is new in kind (not families/tiers/archetypes/project
   types), add it to `packApplies` with unit tests.
4. **Golden cases**: add cases covering a room where the pack applies, one where it does not, and one where facts are missing
   (PENDING_INFORMATION); review the expected outputs with the domain engineer before committing them.
5. **Evidence kinds**: if a new evidence kind is needed, add it to `V25_EV.json` and make sure `recordBlockers` accepts it only for the
   tests that list it (`packages/commissioning-engine/src/recording.ts`).
6. **Server and database**: nothing to change — plans are compiled server-side (`services/enterprise-api/src/domain/rooms.ts`
   `analyze`) and stored as `cx_plan` / `cx_plan_row`; recompilation happens when the plan signature changes.
7. **Tests**: `node --test packages/commissioning-engine/dist/test/**/*.test.js`, then `tests/integration/api.test.mjs` (a room with
   the pack shows the new rows; the responsible persona can record; others get 403).
8. **Docs**: list the pack in `docs/algorithms/ENGINE_INVENTORY.md` (Commissioning Intelligence Engine) with its rules.

## B. Adding a product domain (e.g. Intake requests and decisions)

1. **Model**: write the entities, their lifecycle as a state machine, the authorities for each transition (from
   `V25_PERSONAS.json`: `request.submit`, `brief.approve`, `funding.authorize`, `project.decide` …) and the events
   (`V25_EVENTS.json` already has `project.approval_requested`, `project.approval_decided`, `project.funding_authorized` …).
2. **Migration**: tables with `tenant_id`, composite FKs, RLS FORCE, CHECK constraints for states, append-only where the record is
   evidence (decisions, approvals), grants to `empathia_app`.
3. **Pure rules**: transition gates as a pure function in a package (like `lifecycleBlockers` in
   `packages/commissioning-engine/src/lifecycle.ts`), unit-tested.
4. **Domain module** in `services/enterprise-api/src/domain/<domain>.ts`; **routes** in `src/modules/routes.ts`; **relationships**
   to existing records through `relate()` so Search Party sees them; **read model** handler in `src/worker/outbox.ts` if Pro needs it.
5. **Contract** regeneration, **client** types, **UI** pages, and the three test layers — as in `HOW_TO_ADD_A_FEATURE.md`.
6. **Product docs**: add the domain to `docs/product/PRODUCT_ARCHITECTURE.md` capability map and update the product's maturity only with
   evidence (a test that passes) — never by assertion.
